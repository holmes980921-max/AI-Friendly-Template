# AI 지식 문서 진단 가이드 (AI Knowledge Document Diagnostic Guide)

브라우저에서 동작하는, 사내 지식 문서를 **기존 문서 파싱/색인/챗봇(RAG) 시스템에 올리기 전에** 점검하기
위한 진단 도구입니다.

## 실제 목적

회사에는 이미 다음 시스템이 존재합니다.

1. 사내 문서 파싱 포털
2. 사내 색인/검색 시스템
3. 사내 챗봇/RAG 시스템

**이 프로젝트는 새로운 RAG 시스템이나 챗봇을 만드는 것이 아닙니다.**

문제는, 많은 사내 문서가 "사람"을 대상으로 작성된다는 점입니다. 사람은 암묵적 맥락, 약어, 참조,
관계, 조직 지식을 이해할 수 있지만, AI/RAG 시스템은 문서의 일부만 검색해서 그 의미를
추론해야 하는 경우가 많습니다.

이 도구는 다음 질문에 답하는 것을 돕습니다:

> "이 문서에서 AI가 추론해야 할 수도 있는 부분은 어디인가? (정의, 맥락, 관계, 구조가
> 충분히 명시되지 않은 부분)"

문서를 자동으로 고치지 않습니다. 규칙 기반으로 "확인이 필요한 부분"을 짚어 주고, 문서
작성자가 직접 보완하도록 안내합니다.

## 무엇을 하는가

1. 사내 지식 문서를 붙여넣습니다 (기술 문서, 작업 지침, 트러블슈팅 가이드, 공정 지식, 사내
   가이드라인, FAQ성 지식, 엔지니어링 노트 등).
2. **진단하기**를 클릭합니다.
3. 문서 진단 결과를 확인합니다:
   - 요약 대시보드 (우선 확인 / 확인 권장 / 참고 — 검증된 점수가 아닌 휴리스틱 지표)
   - 우선 확인 항목
   - 상세 진단 (카테고리별로 그룹화, 심각도 필터 가능)
   - 확인 질문 목록 — 문서 작성자가 직접 답하며 문서를 보완할 수 있는 질문들
   - 문서 구조 (감지된 구조적 신호)
   - 권장 문서 구조 가이드
4. 문서 작성자가 필요한 내용을 직접 보완합니다.

이 도구는 문서의 **사실관계가 맞는지**를 판단하지 않습니다. 다만 AI가 이 문서만(혹은 일부만)
보고 의미를 추론해야 하는 지점이 어디인지 짚어 줍니다. 예를 들어 "기존 조건으로 진행한다"에서
사람은 "기존 조건"이 무엇인지 알고 있을 수 있지만, RAG 시스템이 이 문장만 검색한다면 그
의미를 추론해야 할 가능성이 있습니다.

## 입력 방식: 일반 문서 vs Excel 붙여넣기

붙여넣기 textarea 하나로 두 가지 입력을 모두 받습니다. **XLSX 파일 업로드나 바이너리
파싱은 지원하지 않으며, 앞으로도 추가하지 않습니다.** Excel 데이터는 항상 "Excel에서
셀 선택 → Ctrl+C → 이 도구에 Ctrl+V"로만 들어옵니다 (클립보드 TSV 텍스트).

- 일반 문서(prose)로 보이면 기존과 동일하게 문단/줄/문장 단위로 분석합니다.
- 탭으로 구분된 여러 행(= Excel에서 복사한 표)으로 보이면 표 구조를 그대로 보존하는
  별도 경로로 분석합니다. 빈 셀은 위쪽 행의 값으로 자동 채우지 않습니다.

### 병합 셀(merge) 문제에 대한 처리 원칙

Excel에서 셀이 병합되어 있어도, 클립보드에 복사되는 순간 그 정보(병합 여부)는 사라지고
"첫 행에만 값이 있고 나머지 행은 빈 셀"인 TSV 텍스트만 남습니다. 이 도구는 그 빈 셀을:

- **자동으로 채우지 않습니다** (예: 위 행의 "KKK"를 복사해서 채워넣지 않음)
- **병합되어 있다고 단정하지 않습니다** ("병합되었습니다"라고 말하지 않음)
- **비어 있다고 단정하지도 않습니다** ("누락되었습니다"라고 말하지 않음)

대신 "위쪽 행에 있던 값과 관련이 있을 수 있으나, 붙여넣은 데이터만으로는 확인할 수
없다"는 **구조적 불확실성**으로 진단하고, 원본 Excel에서 확인할 것을 안내합니다. 이
원칙은 도구 전체의 핵심 원칙("문서를 추측하지 말고, 불명확한 지점을 진단하라")과 동일한
연장선에 있습니다.

빈 셀이 "구조적 불확실성"으로 표시되는 것은 단순히 "위에 값이 있었다"는 이유만으로
결정되지 않습니다. 오른쪽에 있는 다른 열이 해당 빈 칸들에 걸쳐 실제로 값을 갖고 있어야
(즉, 그 행들이 진짜 개별 항목이라는 구조적 근거가 있어야) 표시됩니다. 그렇지 않으면
("비고"처럼 원래 선택적으로 비워두는 필드일 수 있으면) 그냥 빈 셀로 남습니다 — 근거가
부족할 때는 경고보다 침묵을 택합니다.

### 표 첫 행을 헤더로 단정하지 않음 (다단/병합 헤더 대응)

파서는 붙여넣은 표의 첫 행을 무조건 "헤더"로 간주해 잘라내지 않습니다. 모든 행을 그대로
보존한 뒤, "여러 열을 하나의 라벨로 묶는 것처럼 보이는 행"(값-공백-값이 반복되는 행)을
소프트한 힌트로만 별도 표시합니다 (`possibleHeaderRowIndices`). 이 구분은 오직 미리보기에
"다단 헤더 구조가 포함되어 있을 가능성이 있습니다"라는 안내를 보여주기 위한 것이며, 셀
분류나 진단 로직을 바꾸지 않습니다.

이 설계 덕분에 다음과 같은 다단/병합 헤더 구조에서도 "KKK"가 여러 행에 걸친 상위
맥락일 가능성을 놓치지 않습니다:

```
KKK   정상 조건            이상 조건
      두께   온도   시간    두께   온도   시간
      100~200nm 90~95℃ ...  <100nm ...
```

이전 구현은 첫 행을 헤더로 잘라내고 두 번째 행부터 "데이터"로 취급했기 때문에, 1열의
"KKK 다음에 오는 빈 셀들"이 데이터 영역 밖에 있어 구조적 불확실성 탐지 대상에서 아예
제외되는 문제가 있었습니다. 지금은 모든 행이 동일하게 분석 대상이 됩니다.

## 진단 카테고리 (V1)

| 카테고리 | 확인하는 것 |
| --- | --- |
| 문서 목적 | 문서가 세부 내용으로 바로 시작되어 목적/주제가 드러나지 않는지 |
| 적용 범위 | "제품에 따라", "상황에 따라" 등 범위가 암묵적으로 전제된 표현 |
| 용어 정의 | 문서 내에서 정의되지 않은 약어/사내 용어/코드 (예: PR, ABC) |
| 모호한 표현 | 적절히, 충분히, 정상적으로, 필요하면 등 판단 기준이 불명확한 표현 |
| 맥락 누락 | "이 조건으로", "이 결과" 등 문서 밖의 배경 지식을 전제로 한 서술 |
| 모호한 참조 | 기존 조건, 담당자, 해당, 이전 결과 등 참조 대상이 불명확한 표현 |
| 조건 / 예외 | 조건에 따라 달라진다고 되어 있으나 조건별 대응이 명시되지 않은 경우 |
| 관계 연결 | 문제-원인-조치처럼 서로 관련된 정보의 연결 관계가 불명확한 경우 |
| 정보 혼합 | 배경/조건/절차/예외/결과가 한 문단에 뒤섞여 있는 경우 |
| 중복 / 상충 | 동일 대상에 대해 서로 다른 내용이 문서 내 여러 곳에 있는 경우 |
| 문서 구조 | 제목/목적/절차/예외 등 구조적 신호(소제목)가 거의 없는 경우 |
| 메타데이터 | 담당 조직/버전/적용일 등 메타데이터가 없는 경우 (일정 분량 이상 문서에 한함) |

각 진단 항목은 휴리스틱 심각도(HIGH/MEDIUM/LOW/INFO)와 신뢰도를 가지며, 과학적으로
검증된 점수가 아닌 참고 지표입니다.

## 프로젝트 구조

```
src/
  types/
    diagnostic.ts        Finding 진단 스키마, Category/Severity 레이블
    document.ts           ParsedDocument, TableGrid/TableCell (표 구조 표현)
  utils/
    textParser.ts        입력 종류를 감지해 prose/table 경로로 분기, ParsedDocument 생성
    tableDetector.ts     탭으로 구분된 표 형태 입력 감지 (과도하게 공격적이지 않게)
    tsvParser.ts         TSV를 원본 그대로 grid로 파싱 (빈 셀 보존, 자동 채움 없음)
    structureAnalysis.ts 문서 내 구조적 신호(소제목) 감지
  rules/            규칙 엔진 — 카테고리별 파일로 분리, 확장 용이:
                      purposeRules.ts, scopeRules.ts, definitionRules.ts,
                      ambiguityRules.ts, contextRules.ts, referenceRules.ts,
                      conditionRules.ts, relationshipRules.ts,
                      atomicKnowledgeRules.ts, duplicationRules.ts,
                      structureRules.ts, metadataRules.ts,
                      tableStructureRules.ts (표 병합/구조 불확실성 진단),
                      ruleEngine.ts (통합), helpers.ts (공통 유틸)
  components/       UI: InputPanel, DocumentPreview, TablePreview, Dashboard,
                      FindingsList, FindingCard, ReviewQuestions,
                      DocumentStructure, DocumentTemplateGuide, severityStyles
  sample/           내장 예시 문서(PR 공정 대응 가이드) + 예시 표(병합 셀 예시)
  App.tsx           입력 -> 문서 파싱 -> 규칙 엔진 -> UI 연결
```

아키텍처 (백엔드 없음, LLM 없음, 영구 저장 없음):

```
입력 (붙여넣기)
  -> 입력 종류 감지 (prose vs TSV/표)
       -> prose 파서 (문단/줄/문장 분리)
       -> TSV 파서 (행/열/빈 셀/구조적 불확실성 보존)
  -> ParsedDocument (통합 표현 — 두 경로 모두 동일한 형태로 규칙 엔진에 전달)
  -> 규칙 엔진 (rules/*, prose·표 출처를 구분하지 않고 동일하게 동작)
  -> 진단 결과 (Finding[])
  -> UI
```

### V2 호환성

모든 `Finding`은 `source: 'rule' | 'llm'`과 `confidence` 필드를 가집니다. V1은 규칙
엔진에서 나온 `source: 'rule'` 진단만 생성합니다. 향후 V2의 LLM 기반 의미 분석 레이어는
동일한 스키마로 `source: 'llm'` 진단을 추가할 수 있으며, 이를 위해 UI나 규칙 엔진을
다시 설계할 필요가 없습니다.

향후 구상(V2, 미구현):

```
문서
  -> 규칙 기반 분석
  -> LLM 의미 분석
  -> 통합 진단 결과
  -> 사람의 보완
  -> 기존 사내 문서 파싱 포털
  -> 기존 색인 시스템
  -> 기존 사내 챗봇
  -> 답변 품질 평가
```

## 로컬 실행

Node.js 20 이상이 필요합니다.

```bash
npm install
npm run dev
```

터미널에 출력되는 로컬 주소(예: `http://localhost:5173`)를 브라우저로 엽니다.

## 빌드

```bash
npm run build
```

`dist/`에 정적 사이트가 생성됩니다. 빌드 과정에 타입 체크(`tsc -b`)가 포함됩니다.

빌드 결과를 로컬에서 미리 보려면:

```bash
npm run preview
```

## 테스트

```bash
npm run test
```

`vitest`로 파서/규칙 엔진 단위 테스트를 실행합니다. 표 감지, 빈 셀 보존, 병합 셀
구조적 불확실성 진단, 기존 산문 샘플 회귀 등을 검증합니다.

### XLSX 파일을 이용한 수동 테스트

이 도구는 XLSX 파일을 직접 열지 않습니다 (의도적으로 지원하지 않음). 병합 셀이 있는
Excel 파일(예: `병합셀_테스트_지식문서.xlsx`)을 테스트하려면:

1. Excel에서 파일을 직접 엽니다.
2. 확인하고 싶은 표 범위를 선택합니다.
3. Ctrl+C로 복사합니다.
4. 이 앱의 입력창에 Ctrl+V로 붙여넣습니다.
5. 표 구조가 그대로 보존되는지, 미리보기에서 빈 셀이 "확인 필요"로 표시되는지 확인합니다.
6. 진단하기를 눌러 병합 셀 관련 진단(적용 범위 카테고리)이 생성되는지 확인합니다.

## 배포

`dist/`의 빌드 결과물은 완전한 정적 사이트입니다 — 서버 코드, 환경 변수, API 키가
필요 없습니다. 정적 파일을 서빙할 수 있는 곳이면 어디에나 배포할 수 있습니다:

- **Netlify / Vercel / Cloudflare Pages**: 빌드 명령을 `npm run build`, 배포 디렉터리를
  `dist`로 지정
- **GitHub Pages**: `npm run build` 실행 후 `dist/`를 `gh-pages` 브랜치에 배포
- **사내 정적 파일 서버**: `dist/`의 내용을 그대로 복사

백엔드, 데이터베이스, API 키가 어느 시점에도 필요하지 않습니다.

## 개인정보 보호

모든 파싱과 분석은 브라우저 내 클라이언트 사이드 JavaScript/TypeScript로 수행됩니다.
붙여넣은 문서는 서버, 외부 API, 분석(analytics) 서비스로 전송되지 않으며, 영구적으로
저장되지도 않습니다. 이는 사내의 민감한 지식 문서를 다룰 수 있다는 이 도구의 사용
목적상 중요합니다.

## V1이 아닌 것 (의도적으로 만들지 않은 것)

- 챗봇, RAG 시스템, 문서 색인/파싱 시스템이 아닙니다 (이미 사내에 존재함)
- 문서를 자동으로 고치거나, 정의를 자동으로 생성하지 않습니다
- 백엔드, 데이터베이스, 로그인, 클라우드 저장소가 없습니다
- LLM API를 호출하지 않습니다
- 문서가 "사실관계상 맞는지"를 판단하지 않습니다 — AI가 추론해야 할 가능성이 있는
  지점을 짚어줄 뿐입니다

## 이전 버전과의 차이

이전 버전(V0)은 CVD/TEMP/TIME/RESULT/CODE와 같은 표(테이블) 형태의 정형 데이터를
대상으로 한 "AI Data Friendliness Checker"였습니다. 이번 리팩터링으로 개념 모델 자체가
바뀌었습니다: **"AI 친화적인 데이터베이스 테이블"이 아니라 "AI 친화적인 사내 지식 문서"**를
다루는 도구로 재구성했습니다. 표 데이터 전용 규칙(TEMP/TIME 단위, 컬럼 중복 등)은
모두 제거하고, 문서의 문단/문장 단위 분석으로 대체했습니다.
